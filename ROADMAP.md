# Foosgoos Roadmap

Where the project is, what to do next, and what comes after that.

**Status: Phase 1 complete.** The app records a match as it is played —
every goal is a durable, correctable, timestamped row — and the vision
service is wired up end to end. Nothing has been trained yet. There are no
weights and no labelled data.

---

## The four phases

| | Phase | Ends when |
|---|---|---|
| ✅ | **1. Foundation** | Goals are durable events, matches record video, the camera *can* post goals |
| ▶ | **2. Assisted** | The camera detects most goals; a human taps who scored |
| | **3. Attribution** | The camera knows which rod, and usually which player |
| | **4. Autonomous** | Nobody touches the tablet during a normal game |

Each phase is useful on its own. Phase 2 is genuinely better than manual
scoring even at 70% accuracy, because the failure mode is "you tap a
correction" rather than "you tap everything".

---

# Phase 2 — Assisted mode (you are here)

**Goal: the camera proposes, a human confirms.** A detected goal appears
in the app already counted, marked "needs review", with nobody attributed.
Someone taps who scored, or taps "not a goal".

Everything in Phase 2 is *plumbing you already have* plus *data you do not
have yet*. There is exactly one long-lead item — collecting and labelling
frames — so start it first and do everything else while it runs.

## 2.1 — Get the camera seeing (day one, ~1 hour)

```bash
cd ml && python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python -m pytest tests -q          # passes with no hardware
python -m camera.threaded_camera   # steady, believable FPS?
```

Then calibrate — five minutes, no ML involved:

```bash
python -m tools.calibrate_corners     # click the 4 table corners
python -m tools.watch_ball --no-model # click points, read coordinates
```

Write what you measure into `ml/config.py`: `GOAL_LINE_BLUE`,
`GOAL_LINE_RED`, `GOAL_MOUTH_Y_MIN/MAX`, and the eight entries in
`ROD_POSITIONS`. **The shipped values are placeholders from an example and
are wrong for our table.** No amount of model training fixes a wrong goal
line.

> **Because our table moves daily**, `calibration.json` goes stale. Re-run
> `calibrate_corners` whenever it has been nudged. The Architect model
> (2.6) removes this chore permanently — but do not let it block you now.

**Done when:** clicking each of the four corners reads back approximately
(0,0) (1,0) (1,1) (0,1), and you have measured goal lines in config.

## 2.2 — Start recording every game (day one, ~30 min)

Run the backend and the app, and start a game through the normal flow.
`CreateGame` now creates the match on the server before anyone plays, so
the vision service has something to attach to:

```bash
# terminal 1
cd backend && uvicorn app:app --reload
# terminal 2
cd frontend && npm run dev
# terminal 3, on the camera machine
cd ml && python -m vision_service --preview
```

Play normally. Score by tapping, as you do today. In the background you
are now generating the two things everything else depends on:

1. **Video of every match**, in `ml/recordings/`, with a sidecar frame
   index so any moment can be found exactly.
2. **A goal log with `video_ts_ms` on every goal** — ground truth,
   generated by people simply using the app, with nobody labelling
   anything.

**Do this before anything else, and keep doing it.** Every evening of play
you record before the model exists is an evening of free training data and
free evaluation data. Every evening you do not record is gone.

**Done when:** `ls ml/recordings/` shows an .mp4 and a .frames.json per
match, and `GET /matches/<id>` shows goals with non-null `video_ts_ms`.

## 2.3 — Play ~10 games (a week or two, calendar time not work time)

Aim for variety, not volume: different times of day, blinds open and shut,
overhead light on and off, different people in different clothes. A model
trained on ten games played under one lighting condition will fall over
the first time someone plays at night.

**Done when:** ~10 recorded matches with, between them, 50+ real goals.

## 2.4 — Extract, label, train (one evening of labelling + an hour of GPU)

```bash
python -m data_collection.extract_frames --match 42   # repeat per match
```

This pulls every 20th frame plus a dense burst around each recorded goal.
The bursts matter: the frames around a goal are the fast, motion-blurred
ones, and a model that has only seen a crisp stationary ball loses it
exactly when it matters.

Label in Roboflow — **`ball` only, one class.** Aim for 300–500 varied
frames total. Include some frames with no ball visible; negatives teach
the model what "no ball" looks like.

Then:

```bash
python -m training.dataset_check ./scout_dataset   # ALWAYS first
modal volume create foosgoos-scout-data
modal volume put foosgoos-scout-data ./scout_dataset /data
modal run training/train_scout_modal.py
modal volume get foosgoos-scout-weights <path> ./models/gameplay_v1.pt
```

`dataset_check` catches the things that quietly waste an hour of GPU
time — unlabelled images, empty splits, coordinates out of range. Run it
every time.

**Done when:** `mAP50 > 0.85` on the validation split. If it is much
lower, the labels are inconsistent — go and look at them; do not train
longer or bigger.

## 2.5 — Tune against footage, not at the table

This is the step people skip and then wonder why nothing works.

```bash
python -m inference.live_pipeline --source ml/recordings/match_00042.mp4
python -m evaluation.evaluate_goals --match 42
```

The evaluator replays a real game through the same code that runs live and
scores it against what the humans recorded:

```
  recall     91.7%   (11/12 real goals found)
  precision  84.6%   (11/13 calls were real)
  latency    median +0.31s
```

Iterate here. A ten-minute game replays in seconds, so you can try twenty
threshold values in the time it takes to play one point at the table.

| What you see | What to change |
|---|---|
| misses clustered at one end | `GOAL_LINE_*` for that end |
| ball seen in <60% of frames | more training data, not more thresholds |
| phantom goals mid-table | tighten `GOAL_MOUTH_Y_MIN/MAX` |
| phantom goals just after a real one | raise `GOAL_COOLDOWN_S` |
| missed slams, caught taps | raise `MAX_BALL_SPEED`, check inference fps |

**Done when: recall ≥ 90% and precision ≥ 90% across at least 3 matches
you did not tune on.** Hold that line. Tuning until it is perfect on one
match and calling it done is how you ship something that works once.

## 2.6 — Train the Architect (optional here, but you will want it)

Because the table drifts daily, a hand-clicked calibration needs redoing
constantly, and a stale calibration silently degrades every coordinate.

Collect ~100 empty-table frames (`record_dataset --mode table`), label 4
keypoints each in the fixed order, train, drop in `table_v1.pt`. The
pipeline picks it up automatically and stops using `calibration.json`.

**Done when:** `homography.source` reads `architect` at startup, and
bumping the table produces a `[homography] table moved` line followed by
correct coordinates.

## 2.7 — Go live in assisted mode

```bash
python -m vision_service
```

Camera goals appear in the app already counted, highlighted for review.
Somebody taps who scored. Manual buttons keep working exactly as before —
they are the fallback whenever the camera is being weird.

**Phase 2 is done when a normal evening of foosball produces correct
scores with people tapping only "who scored", not "a goal happened".**

# Phase 3 — Attribution

Now the camera knows *that* a goal happened. Phase 3 is about *who*.

**The hard part, stated honestly.** The rods interleave:

```
blue goal |  bG   b2   r3   b5   r5   b3   r2   rG  | red goal
```

Blue's attacking 3-bar sits deep in red's half, right beside red's 5-bar.
So ball position alone cannot identify whose rod touched it — that is why
`config.SEND_BAR_HINT` is `False` today and `zones.rod_hint()` answers
`"unknown"` in the middle of the table. This is a real geometric fact, not
a modelling shortcut.

Doing it properly needs three things:

**3.1 — Detect rod men.** Add `player_red` / `player_blue` classes to the
Scout dataset. Two classes, not ten — you get the rod *identity* from
which x-position the man is at, because rods only move along y.

**3.2 — Detect the strike.** A rod hits the ball when the ball's velocity
changes discontinuously *and* a rod man is adjacent at that instant. That
event, not the ball's position, is what identifies the rod. Log candidate
strikes to a file for a few games and check them against footage before
trusting any of it.

**3.3 — Map rod to human.** This part is already solved: the app knows who
is playing offense and defense, and `swapPositions` tracks mid-game
swaps. Rod → position → person.

**Phase 3 is done when:** the goal appears pre-filled with the right
player and rod, and the human's tap is "yes" rather than "here is who it
was". Measure it the same way — extend `evaluate_goals.py` to score bar
and player accuracy, not just team.

Also worth doing in this phase:
- **Saves.** `PlayerStats.saves` exists and is always 0. A save is a shot
  that entered the goal mouth and left without crossing — you already have
  the trajectory to detect that.
- **Possession and shot counts.** Cheap once the ball is tracked reliably,
  and much more interesting on a stats page than goal totals.

# Phase 4 — Autonomous

Only attempt this once Phase 3 accuracy is boring.

**4.1 — Detect the game, not just the goals.** Serve detection (ball
appearing at the serve hole), end-of-game detection (a team reaching the
target score), maybe table-occupancy detection so a game can begin without
anyone opening the app first.

**4.2 — Invert the flow.** Today: pick players → camera watches. Then: the
camera notices a game starting and asks *"who's playing?"* on a screen by
the table. That is the only human input left.

**4.3 — Recognise players.** The genuinely hard version. Realistic
alternatives, in increasing order of effort: a "same teams again" button,
NFC tags or phone check-in, and only then anything involving vision.

**4.4 — Trust and repair.** Autonomous means nobody is watching, so the
system must be honest about uncertainty: flag low-confidence games for
review afterwards rather than silently writing wrong stats. A stats page
nobody believes is worse than one nobody has.

---

## Working principles

**Record everything, always.** Storage is the cheapest thing in this
project. A game you did not record is data you can never get back.

**Measure before tuning.** `evaluate_goals.py` on real footage is the only
opinion that counts. "It looked right when I watched it" is not a number.

**Prefer honest uncertainty to a confident guess.** `bar = "unknown"` is a
feature. A wrong prefill costs more than a blank one, because someone has
to notice it first, and they will not.

**Keep the seams.** `ml/` and `backend/` talk over HTTP and nothing else.
That is what lets the entire vision stack be replaced without touching the
API — and it will be, at least once.

**One model at a time.** Ball detection, then rod detection, then anything
else. Each one is separately checkable; a change in all three at once is
not debuggable.
